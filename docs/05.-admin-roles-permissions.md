# Admin Roles & Permissions

## 1. Purpose

Organic Powder is designed to support multiple people working on different parts of the business.

One person should not be responsible for managing products, inventory, orders, payments, marketing, customer support and other operations at the same time.

To solve this, the platform uses **roles and permissions**.

Each staff member is assigned a role based on their responsibilities. Their account gives them access only to the sections of the Admin Portal that they need for their work.

For example:

* A Product Manager manages products.
* An Inventory Manager manages stock.
* An Order Manager manages orders.
* A Marketing Manager manages coupons and campaigns.
* A Finance Manager manages payments and refunds.
* An Analyst can view reports but cannot modify business data.

This makes the platform easier to operate, more secure and easier to maintain.

# 2.2 Admin / Staff

Admin and staff users operate the internal side of the Organic Powder platform.

Instead of giving every staff member complete administrator access, each person receives a specific role based on their responsibilities.

```text
                         ADMIN / STAFF
                              |
              +---------------+---------------+
              |               |               |
          Products        Operations       Business
              |               |               |
          Inventory         Orders          Finance
          Content           Shipping        Marketing
          AI                Support         Analytics
          Procurement
```

The **Super Admin / Owner** has control over the complete platform, while other staff members receive limited permissions.

# 4. Role vs Permission

A **role** represents a person's responsibility within the business.

For example:

```text
Marketing Manager
```

A **permission** represents a specific action that the user is allowed to perform.

For example:

```text
coupons.read
coupons.create
coupons.update
coupons.delete
```

Therefore:

```text
Marketing Manager
        ↓
Assigned Permissions
        ↓
+---------------------+
| coupons.read        |
| coupons.create      |
| coupons.update      |
| coupons.delete      |
+---------------------+
```

The role provides the business-level responsibility, while permissions define the actual capabilities.

This approach is called **Role-Based Access Control (RBAC)**.

# 6. Principle of Least Privilege

Every staff member should receive only the permissions required to perform their responsibilities.

For example:

```text
Product Manager
        ↓
Products
        ↓
Read + Create + Update
```

They do not automatically receive:

```text
Refund Payments
Manage Staff Roles
Change System Settings
```

Similarly:

```text
Analyst
   ↓
Analytics
   ↓
Read Only
```

This reduces the possibility of accidental or unauthorized changes.

---

# 7. Backend Authorization

Permissions must be enforced on the **backend**, not only in the frontend.

The frontend can hide UI elements that the user does not have permission to use, but this is only a user-experience feature.

The backend must perform the actual authorization check.

The expected flow is:

```text
User Request
     ↓
Authentication
     ↓
Identify User
     ↓
Identify Role
     ↓
Check Permission
     ↓
Allow / Reject Request
```

For example:

```text
Marketing Manager
       ↓
POST /api/coupons
       ↓
Check coupons.create
       ↓
Permission exists
       ↓
Create Coupon
```

If the permission does not exist:

```text
Request
  ↓
Permission Check
  ↓
Permission Missing
  ↓
403 Forbidden
```

# 8. Future RBAC Implementation

The planned authorization structure is:

```text
User
  ↓
Role
  ↓
Permissions
  ↓
Protected Resource
```

For example:

```text
User
  ↓
Marketing Manager
  ↓
coupons.create
  ↓
POST /api/coupons
```

Another example:

```text
User
  ↓
Analyst
  ↓
analytics.read
  ↓
GET /api/analytics
```

This structure allows the system to add new roles or permissions without rewriting authorization logic throughout the application.

# 9. Administrative Accountability

Important administrative actions should be recorded in an audit log.

The system should be able to answer:

```text
Who performed the action?
What did they change?
When did they change it?
Which resource was affected?
What was the previous value?
What is the new value?
```

Example:

```text
Product: Beetroot Powder — 500g

Action: Price Updated

Previous Price: ₹399
New Price: ₹449

Changed By: Product Manager
Date: 2026-09-17
```

This makes sensitive business operations traceable.

---

# 10. Role Design Principle

Organic Powder uses role-based access to separate business responsibilities.

The goal is not to create as many roles as possible.

The goal is to make sure that:

* Each person understands their responsibility.
* Each person sees the tools they need.
* Sensitive operations are restricted.
* Important actions are traceable.
* The backend controls access securely.
* New roles and permissions can be added as the business grows.

The Admin Portal is therefore designed as **one platform with role-specific access**, rather than a completely separate application for every employee.

```text
                         Admin Portal
                              |
                         Authentication
                              |
                           User Role
                              |
                         Permissions
                              |
              +---------------+---------------+
              |               |               |
           Products        Operations       Business
              |               |               |
          Product Mgr      Inventory        Marketing
                           Orders           Finance
                           Shipping         Support
                           Procurement     Analytics
                           Content
                           AI
```

The final objective is to make the administrative system **secure, understandable, maintainable and scalable as the business grows**.
